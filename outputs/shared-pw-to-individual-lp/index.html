Pain Points / いまのツラさ

いまのやり方、ここがツラい

01

入職者が来るたびに、手作業でアカウントを発行している

メール共有・管理者呼び出し・マニュアル設定。入職のたびに担当者が動く必要がある。

02

退職者のアカウントが止められず、残り続ける

共有パスワードを変えると全員に影響する。退職者の権限を即時無効化できない構造になっている。

03

誰が何を使っているか、把握できていない

共有アカウントではログが「誰が」やったかを示さない。監査・コンプライアンス対応が不可能。

04

「個別化したい」が、管理コストが怖くて踏み出せない

1人ずつ設定・管理・削除……手作業では追いつかない。だから共有のまま使い続けている。

共有している理由が「管理アカウントを作るのが困難」だったなら、
その「困難」を仕組みで代替することで、共有はやめられる。

¥1,538,842 の管理コストを、Slackだけで完結する設計に置き換える。
担当者が覚えることは「ボタンを押す」だけ。

Auth Strategy / 認証設計

これは、認証資産を
潰さず"進む"一手。

既存のパスワード運用を全廃するのではなく、
OTP（ワンタイムパスワード）を重ねることで
現行の認証資産を活かしたまま、
ガイドライン準拠の多要素認証に移行できる。

一挙に切り替えるリスクを取らず、
段階的に準拠レベルを上げる設計を採用する。

Scope Note / 注記

ただし、認証は"一部"から。

すべてのSaaSを一度に個別化・自動化する必要はありません。
リスクの高いツール・頻度の高い操作から段階的に移行することで、
現場への負荷を最小化しながら準拠レベルを上げていきます。

スコープと優先順位の目安
Phase 1（即着手） 最重要SaaS（採用管理・人事系）の個別化 + Slack Bot構築
Phase 2（〜3ヶ月） OTP認証の導入・全SaaS API連携の拡張
Phase 3（〜6ヶ月） 台帳・監査ログの整備・定期レポート自動化
対象外 ローカルインストール型ツール・外部委託先のSaaSアカウント（別途検討）

ガイドラインが求めるのは「全部一度に完璧に」ではなく、
「リスクを認識し、計画的に改善していること」です。
Phased移行は、準拠の観点でも正しいアプローチです。
